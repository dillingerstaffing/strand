# A geometry a consumer needs to set is a custom property with today's value as its fallback

Where a consumer legitimately needs a different width, height, floor or offset than the default (`--strand-avatar-bg` and `-fg`, `--strand-btn-min-block-size`, `--strand-calendar-grid-day-size`, `--strand-data-readout-value-size` and `-label-size`, `--strand-dialog-inline-size`, `-radius`, `-edge` and `-block-size`, `--strand-search-field-inline-size`, `--strand-nav-slot-reserve`, `--strand-tabbar-height`, `-item-size`, `-label-size` and `-justify`, `--strand-ref-sticky-top`, `--strand-scroll-col-h`, `--strand-sticky-top`, `--strand-reserve-h`, `--strand-grid-split-panel`), the primitive reads a custom property whose fallback is exactly the value it shipped with, so an untouched consumer renders unchanged and setting the property is design-system usage where overriding the class would be a workaround. The fallback lives inside the `var()`, never in a declaration of its own on the block: `.strand-data-readout__value` is composed without its block in real markup, and a property declared only on the block would leave that orphan resolving an unset variable, which is invalid at computed-value time and makes an inherited property inherit. A knob is one number; a change that also moves padding or type is a modifier. Continuous values (a per-person tint, a width) are properties, never an enum of variants; size modifiers that exist are set on the block itself so a modifier always beats an ancestor's declaration.

Where: the component stylesheets named above; `docs/cf/surface-tokens.md` for the colour tokens that follow the same rule.
